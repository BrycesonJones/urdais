# Brief for the global data-centre research expansion

What the next research pass is for, what it must produce, and the rules it works
under. Written 17 September 2026, when methodology 2.0.0 opened the data-centre
scope. Nothing here has been researched yet; this is the handoff.

The methodology is `docs/methodology/map-facilities.md` (version 2.0.0). Read it
first — this brief does not restate it, it says how to work under it.

## What changed, in one line

A data centre is now on this map **because it exists**, not because it matters
to AI. AI relevance is enrichment recorded separately, with its own evidence.

## What to produce

A dataset file in the import contract, version
**`urdais.map.facility-import/2`**, plus the research Markdown it was projected
from. Dry-run it with `npm run map:import -- --file <path>` and read every error
and review candidate before proposing a write.

Do **not** extend `data/map/facilities.v1.json`. That file is the projection of
the Phase 1 research package and is regenerated by `npm run map:project`; a new
pass gets its own research document and its own dataset file.

## The two jobs, in order

**A. Remediate the existing 78.** Forty-two records persist with no position and
cannot be shown. They are the cheapest coverage available, because the facility
is already identified and evidenced — what is missing is one documented address
or coordinate. Seven more are in the review queue for stated reasons; see
`docs/operations/map-phase-3-dataset-review.md`, which lists each and what would
resolve it.

**B. Expand the universe.** Global data centres under the new inclusion rule.
Prefer breadth of *markets* over depth in the ones already covered: the current
dataset is 20 published facilities in the United States and 9 everywhere else,
which is a picture of where the research looked rather than of where data
centres are.

## Working rules, in the order they will bite

1. **Existence is the criterion.** Colocation, carrier-neutral, wholesale,
   enterprise, sovereign, HPC hosts, carrier hotels that materially function as
   data centres. No GPU, no AI tenant, no capacity figure, no known operator —
   all fine. See methodology §2.1 for the full include and exclude lists.

2. **A region is not a facility.** Never infer a building from a cloud region,
   an availability zone or a geographic label. Do not create a record for an
   edge node with no facility identity, a rack or cage inside another facility,
   or a directory entry that cannot be corroborated as a real place.

3. **Directories are for discovery.** Use them — a global inventory cannot be
   built without them. But a directory entry alone never places a public dot.
   Positioning evidence must be one tier 1–2 document (operator page, permit,
   filing, planning record, reputable press, property record) **or** two
   directories *from different publishers*. Record directory sources with
   `documentType: "facility_directory"`; the importer counts publishers and will
   refuse a batch that tries to publish on one.

4. **Never invent a position.** No city or metro centroids, no guessed
   industrial parks, no borrowing a neighbour's coordinates because a
   relationship exists. A documented street address that has not been geocoded
   is a *valid record* — set `coordinatePrecision: "street"`, leave latitude and
   longitude null, and it persists as research until somebody geocodes it.

5. **AI relevance is a separate question with its own evidence.** Set
   `aiRelevance` to one of `documented_ai`, `ai_capable_or_high_density`,
   `no_documented_ai`, `unknown`. Either positive state needs at least one
   `ai_relevance` claim on a cited source, and the database will refuse it
   otherwise. Use `no_documented_ai` only when you actually reviewed sources and
   found nothing — it does **not** mean the facility cannot run AI. Leave
   `unknown` when nobody looked. Never infer capability from size, power draw,
   the operator's other sites, or a metro's reputation.

6. **Entity granularity.** One named facility or campus. A multi-building campus
   the operator presents as one campus is one record; separately named buildings
   are separate records when sources distinguish them. Do not explode a campus
   into buildings, and do not collapse named sites into a metro. A landlord and
   its tenant are **not** two `data_center` records for one building — the
   building is the data centre, and an evidenced tenant deployment is a
   `gpu_compute_cluster` connected by `hosted_by`.

7. **Shared coordinates never merge two records.** The importer remarks on them
   and merges nothing; so should you.

8. **Nothing else broadens.** GPU clusters still need an identifiable physical
   system. Fabs keep the AI supply-chain rule. Power infrastructure still needs
   an evidenced `supplies_power_to` edge into compute — do not bring back
   general power-plant research.

9. **Check the rejection register** before adding a candidate:
   `data/map/rejected-candidates.v1.json` holds 38 an earlier pass examined and
   declined, with reasons. A rejection may be overturned by evidence that
   answers it; the importer will remark on any name that resembles one.

10. **Unknown is null.** Never an empty string, never a placeholder, never a
    zero standing in for a missing figure.

## What a good record looks like

```jsonc
{
  "researchKey": "example-operator-amsterdam-1",
  "canonicalName": "Example Operator Amsterdam 1",
  "category": "data_center",
  "ownerName": null,                       // unknown is fine
  "operatorName": "Example Operator",
  "aliases": [{ "alias": "AMS1" }],
  "location": {
    "streetAddress": "Voorbeeldweg 1", "locality": "Amsterdam",
    "countryName": "Netherlands", "countryCode": "NL",
    "latitude": 52.3, "longitude": 4.9,
    "coordinatePrecision": "building", "coordinateMethod": "documented_address_geocode"
  },
  "lifecycle": { "status": "operational" },
  "facts": [],                             // capacity is not required
  "evidence": [{
    "publisher": "Example Operator", "title": "AMS1 facility page",
    "url": "https://…", "documentType": "company_facility_page",
    "claims": [{ "field": "location", "statement": "Voorbeeldweg 1, Amsterdam" }]
  }],
  "quality": { "confidence": "high", "lastVerifiedDate": "2026-…", "reviewNotes": [] },
  "aiRelevance": "no_documented_ai",       // reviewed; sources say nothing about AI
  "requestedPublicationState": "published"
}
```

That record publishes. It has no GPU, no AI tenant, no megawatts and no owner.

## What to report back

Per facility: the classification (publish / research / review) and why. Per
batch: counts by country, category, lifecycle and AI relevance; the tier mix of
the sources used; every review candidate; and any candidate that resembles a
prior rejection. The dry-run report produces most of this already — read it,
don't re-derive it.

## What not to do

Do not write to a hosted database. Do not bulk-import. Do not republish the
existing 78 under new rules as a side effect of a run — if a re-import restamps
records from methodology 1.0.0 to 2.0.0, the importer will list them in
`result.restamped`, and that list is something to look at rather than scroll
past.
